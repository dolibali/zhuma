# Member workbench v1

Refs #104. This facade reuses the existing WorkbenchService writer, Workbench revision/receipts and AppliedPlan snapshots. It does not register owner RPC, maintain a second project/task store, dispatch nodes, or run a model on reads. `member-workbench-dto.ts` is the concrete typed contract.

## Host seam

A mounts `applyMemberWorkbench(ctx, options)` beside the closed legacy owner routes, using the **same opened WorkbenchService instance**. A owns plugin lifetime, exports and model wiring. A also opens `openMemberWorkbenchOperations(ctx.storageDomain)` once, passes `handle.journal` as `options.operations`, and closes the handle on disposal. This opens only `zhuma_member_operations` v1 with an `intents` table; absent operation storage leaves snapshot readable and all command capabilities disabled, with commands failing closed. `directory()` supplies B's current SpaceDirectory plus `membersForSpace(spaceId): readonly { id; name? }[]`, intersecting actual identity accounts and current membership. No password verifiers are accepted. Missing names display the real account ID. `writer()` supplies the existing first-assignment-only `assignProjectSpace`. `resolve()` is internal to HTTP and re-resolves the same request cookie at asynchronous authorization boundaries. There is no request-supplied actor.

`catalog(spaceId)` is an optional trusted grant provider for experts/assets. Absent is `resources=not-connected`, with empty projected resources; an explicitly connected, empty provider is `resources=authorized`. Neither case falls back to legacy global experts, skills or MCP. An expert/resource ID collision with a different global definition rejects rather than overwriting another scope. Human IDs are reconciled only after trusted membership; old global profile bytes remain intact and are not used in member prompts or confirmation definitions. C's future available Agent/runtime grant is a separate integration dependency, not implied by `available` or by a legacy expert definition.

## Transport closure

All three operations are POST `/api/zhuma-member/<endpoint>`, `Content-Type: application/json`, with the official `{type:'client-request',rpcId,method:'zhuma-member/<endpoint>',payload}` envelope. Responses use `{type:'server-response',rpcId,result:{ok:true,value}|{ok:false,error:{code,message}}}` and `Cache-Control:no-store`. Connection owns Host/Origin and owner transport admission; a live product member cookie is additionally required. The old global five routes remain closed in multi-member mode.

| Endpoint   | Payload                                             | Value                                     | Authorization and effect                                                                                                             |
| ---------- | --------------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `snapshot` | `{spaceId}`                                         | `MemberWorkbenchSnapshot`                 | Current member and explicit space; only mapped projects, participating tasks and their plan projections. No writes/model/node start. |
| `command`  | `{spaceId,requestId:uuid,expectedRevision,command}` | `MemberWorkbenchSnapshot`                 | Specific object/action checks in the shared writer queue, including retries; one durable Workbench revision. Commands below.         |
| `plan`     | `PlanRequest & {spaceId}`                           | `{actorId,spaceId,proposal:PlanProposal}` | Task owner, participant and project space; explicit configured model only. Proposal is audited, never applied or started.            |

Snapshot includes exact `actorId`, `spaceId`, space metadata, filtered `state:Workbench`, `model:string|null`, and capabilities for creation, planning, resource connectivity and per-task edit/confirm/plan. `state.revision` intentionally remains the shared Workbench revision. `receipts=[]`; other spaces' tasks, assets and participant profiles are not projected. AppliedPlan runtime facts stay unchanged on the server; their Client projection withholds revoked expert/asset definitions and uses trusted current display profiles for humans. This projection must never be submitted back as a runtime authority.

| Command type     | Object                                                          | Rules                                                                                                                                                               |
| ---------------- | --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `create-project` | `project:Project`                                               | New global ID, references from the authorized directory; all current space members may create. Keep the project ID with the same request ID on retries.             |
| `update-project` | `project:Project`                                               | Existing project mapped to this space. No move or reassignment.                                                                                                     |
| `create-task`    | `task:WorkTask` without `status`, `updatedAt`, `templateSource` | New global ID, authorized project, explicit human owner, current actor included, only current authorized participants/resources. Server sets draft and time.        |
| `update-task`    | Same task input                                                 | Existing draft, current actor is task owner and participant, unchanged project. Supports arbitrary validated list/graph/nested edits.                               |
| `confirm-task`   | `taskId`                                                        | Existing draft, owner only; complete valid graph, assignments, outputs and reviewers. Uses the existing `save-task` ready command atomically to create AppliedPlan. |

No command can modify frozen AppliedPlan structure. This batch does not silently reopen a ready task. Plan discovery/start uses the existing execution `startable` / `start-plan`; confirmation itself starts nothing. Existing nested-draft confirmation remains supported, while execution currently returns `child-task-required` pending the child-task container implementation. Do not flatten it or show it as successfully running.

## Ordering, recovery and failures

Writes serialize with legacy commands on the same WorkbenchService queue. Receipt identity hashes actor/space/request ID; trusted actor plus the normalized full request (including space, expectedRevision and command) is fingerprinted. Same-body replay reauthorizes and returns the current authorized projection without a second write; changed-body reuse returns `request-reused`. The existing 200-Workbench-receipt window remains; operation metadata separately retains the most recent 200 completed outcomes. An unresolved pending intent never falls out with either completed window. Other requests require the exact global expectedRevision, otherwise `conflict` before side effects. Do not make a new ID after an uncertain acknowledgement; first retry the original body and ID.

Project creation validates the entire prospective Workbench **before** assigning trusted project space. Directory assignment precedes Workbench durability. On an assignment conflict, reread and accept only the identical space; another space, unknown, closed or unavailable fails closed. Before any directory or Workbench side effect, full object/authorization/budget validation is followed by a durable pending intent containing only actor, space, request ID, object ID, command type, expectedRevision and request fingerprint. A Workbench write failure may leave the intent plus a directory reservation. This is not a visible project or successful creation; the same body, project ID, expectedRevision and request ID can finish after restart. A changed body is rejected even when the first operation never completed. A different create request cannot take over the same pending object. Workbench success is then bound to a completed intent with resultRevision; if completion acknowledgement fails, the existing canonical receipt completes metadata without applying another mutation. If a pending operation has lost that receipt and the Workbench revision has changed, return `operation-unresolved` and preserve the intent; never infer a latest version or reapply to a new revision. Completed metadata is also checked against canonical object/plan presence. There is a total 400-record cap; pending records are never automatically deleted, and saturation rejects new writes with `operation-limit`. Opening, reading and refreshing do not execute pending requests. Never overwrite/delete the reservation to mask failure. Same-host serialized Workbench ownership is required; this is not a distributed transaction across multiple Hosts.

Authorization is repeated after asynchronous lookups and immediately before durability/model dispatch. A cancelled request before Workbench durability does not commit business data (it may retain a pending intent); once storage has accepted a write, cancellation cannot undo it and the original ID resolves the uncertain outcome. Snapshot changes during asynchronous scans return `conflict` rather than stale access. Planning binds actor/space, revision and authorized catalog in its audit fingerprint; catalog revocation/change invalidates cached/base/late proposals. Abort releases the planning slot and late provider output cannot publish; an uncooperative provider may still consume its own resources until its port honors the signal. Only one planning call is admitted by the existing service lock.

Shared body budget is 8 MiB / 10 seconds; whole HTTP operation deadline is 120 seconds and includes Host disposal/caller abort. Workbench's existing caps and strict nested schemas apply. Planning keeps the existing at-most-two validation attempts and audit retention policy. No polling, automatic model retry after interruption, or implicit template fallback. Cancellation returns `cancelled`; missing model `model-unavailable`; stale version `conflict`; changed grant context `context-changed`; incomplete graph `validation`; hidden/wrong space or nonparticipant `not-found`; participant without owner write permission `forbidden`; bad references `resource-unavailable`; ready edits `confirmed-plan`; interrupted/busy planning keep the existing `plan-interrupted`/`planning-busy`. Provider, storage, parser and account-verifier details are never returned. HTTP auth/content/envelope/body failures use 401/403/415/400/408/413 as applicable.

## Evidence boundary

`member-workbench-service.test.mjs` is a service/serialization and rejecting-or-injected-model contract suite; it includes explicit flat AppliedPlan → existing ExecutionService discovery/start and honest nested refusal. `member-workbench-http.test.mjs` composes actual published DSH Connection, identity cookies, space directory and JSON storage in an isolated temporary home, exercising real HTTP and same-disk reopen. `member-workbench-operation.test.mjs` verifies retention, capacity, receipt eviction and uncertain outcomes. `member-workbench-recovery.test.mjs` uses separate real DSH component processes on the same JSON domains, injects failures before/after intent, after assignment and before/after outcome completion, then SIGKILLs the first process before domain close; only explicit original-body retries in a new process resume the operation. Its account enumeration adapter is test-only pending B's directory integration. It does not certify the final Host plugin assembly, desktop UI, an installation, an actual model, native Agent execution or the child-task container. Those remain distinct integration/acceptance gates for A/B/C and the coordinator.
