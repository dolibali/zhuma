# 有界方案设计

## 输入与范围

以任务给出的需求、验收、约束、当前实现或接口为基线。按需读取授权代码和已接受资料；未知接口、部署和运行能力明确待核实，不把经验当当前事实。

## 方法

1. 先写清需要改变的行为、已有能力和不可破坏的约束。围绕本次问题选择最小模块范围，优先复用现有事实来源、执行和存储机制。
2. 对真正影响用户价值、复杂度或风险的取舍，比较首选与少量合理替代；给出采用和放弃理由，以及实现、迁移和维护成本。简单改动不强制长篇选型。
3. 描述模块职责、输入输出、状态或版本边界、必要授权和协作接口。说明并发、部分失败、取消、重试或恢复中与本方案有关的行为，避免凭空设计完整框架。
4. 把关键约束映射到可观察验收与定向负例；把设计预期与已执行验证分开。需要迁移时说明兼容范围、恢复点和失败处置。
5. 提交给独立评审者检查可行性与验收覆盖。重大取舍未定时列出决策点，不代用户批准，也不在同一步偷偷实现。

## 交付

交付方案、主要取舍、接口和依赖、风险与验收依据。供下游计划使用的版本以正常提交并接受的产物为准。

通过任务产物草稿交付；不自动安装依赖、创建服务或写外部系统。最多一轮内容自检，不把自检当正式可行性评审。
