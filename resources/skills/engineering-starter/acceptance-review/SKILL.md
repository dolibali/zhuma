# 验收与内容评审

## 输入与独立性

核对被指派对象的固定版本、验收标准、相关已接受输入及尚未解决的意见。只读取本次有权访问的必要内容；无法读取必需材料时说明证据不足，不换成其他版本。

先确认评审对象属于需求、方案、执行计划还是面向读者的文档。按实际类型读取[评审检查项](references/review-checks.md)中对应部分，不要求补齐与任务无关的文档体系。

## 方法

1. 从目标与验收出发，检查主要内容、依赖和失败条件是否闭环。保留合法的简短上游引用，避免把“没有既存文档”误报为缺失必须存在的文档。
2. 对每项重要发现给出具体内容位置、当前事实、用户影响或失败场景，以及可执行的修正方向。建议与确实阻断交付的问题分开，不为凑数量扩大范围。
3. 处理重提时，核对新固定版本与原意见，标明已解决、部分解决、未解决或不再适用及依据；不要仅因作者说已修复就关闭问题。
4. 给出建议通过、需修改或证据不足的结论，确保结论与发现一致。未验证的运行、性能或授权行为保持未验证，不从文字推定成功。

## 正式评审与交付

交付具名问题、依据和结论。若处于产品的正式评审任务，只能使用当前身份和本轮固定版本对应的正常评审动作；报告中的“建议通过”不产生正式票，也不解除下游阻塞。

评审者不能是该产物执行者；身份或版本不匹配时报告冲突并停止提交。只做一轮结论一致性检查，不自动重复评审或代作者修改并批准自己的结果。
