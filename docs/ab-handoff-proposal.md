# A/B 交接提案与首个联调样例

状态：2026-10-22，A 本批开发中。子任务容器及首轮行为边界已由协调侧确认，具体转换、权限和执行尚未实现。已读取 B PR #1 的 `80b1ff2` 公开契约。本文是 A 的交接方案，不代表 PR 已合入或双方全部冻结。B 的状态机、产物、投票和待办规则由 B 维护，A 不另写。

## 分层版本与身份

- A 的 Participant.id 是唯一目录 ID。对外 human/expert 目录类型保持一致；B 若需执行分类，单独映射 human/agent，不改变目录身份。专家的能力定义不等于 Run 的执行器或模型。真实命令 actor 必须来自 Host 身份，不能从下拉框或浏览器 body 取得。
- Workbench.revision 仅用于当前本地工作台的并发写保护。AppliedPlan.id/revision 是每个任务已确认定义的版本；对象执行 revision 属于 B，绝不能直接复用全局 revision。
- A 已实现 appliedPlans 的持久化确认快照，包括当时的人员、资产和完整节点。继续编辑草稿、修改专家或 Skill 不改变已确认快照。每次重新确认增加计划版本；尚未增加运行中计划升级命令。
- A 的 task.status=ready 当前仅表示定义已确认，UI 显示“已确认、待执行接入”。B node.ready 才是依赖满足可处理；后续接入时 A 只读取 B 的 NodeExecutionReport，不根据 AI 结束或进程退出猜测完成。
- A 的 requestId 幂等回执与工作台 snapshot 在同一次存储中写入；B 的 actor/对象版本命令信封继续由 B 维护。集成时为 A 命令加可信身份封装，不能把本地单所有者模式当作多人授权已经完成。

## 层级模型：建议采用子任务容器

用户场景是公司目标 → 项目工作 → 团队分工 → 个人再拆解。子流程需要独立参与者、负责人、计划确认、执行和可见范围，因此不能只满足画布展开。

| 方案                      | 收益                                                                            | 成本与问题                                                                                                               |
| ------------------------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 同任务 workflows 加作用域 | 当前草稿编辑改动小，整体一次保存                                                | 最终仍要给每个作用域增加负责人、成员、权限、计划版本和状态，实质形成另一套任务容器；一个全局保存还会争抢独立子计划的修改 |
| 子任务容器                | 复用 Task 的参与者、版本、权限和执行语义；与 B 的 parentNodeId/childTaskId 一致 | 拆分必须原子创建子任务并关联父节点；工作树查询需要跨任务聚合；权限裁剪需要服务端实现                                     |

**A 推荐子任务容器**。一个 Task 保存一个根工作流；节点可引用 childTaskId，子 Task 保存 parentNodeId/rootTaskId。完整工作树是这份父子关系的投影，不另存第二棵树。计划内的普通并行仍由同一个工作流依赖边表示。子任务的成员可以独立选择，授权仍需可信服务端判定；看到祖先拓扑不等于能读祖先资料。

当前 `task.workflows[].parentNodeId` 只实现同任务内的嵌套草稿，尚不覆盖独立权限。这批保留可验证的编辑能力，明确不冻结它为执行端树模型。建议双方确认后，由 A 提供一次性转换：根工作流留在原任务，每个嵌套工作流成为一个子任务；保留所有节点 ID，原 parentNodeId 转成子任务归属，父节点指向 childTaskId。新建子任务不隐式启动，也不凭 UI 猜测负责人。

AI 输出可继续使用“嵌套草案”形状，作为一次提案的中间格式；应用时经同一领域命令转换为任务树，并要求确认子任务负责人和参与者。它不是第二份执行事实。

子任务返回必须含版本化汇总产物引用和结束结论；只回到父节点负责人，父节点仍需提交并走原评审。A 不把所有子节点完成直接折叠为父节点已交付。

协调侧已确定的首轮规则（待实现）：

- 父节点执行者为人时，子任务责任人默认该人；为专家时默认父任务的人类责任人。允许在有权限人员中修改；无可用人类责任人则停在草稿，要求选择。
- 取消父任务停止后代新派发，并向正在运行的后代请求取消；真实回执前显示取消处理中和未停止项。归档不隐式取消，有未结束后代时拦住归档。B 负责取消与返回事实。
- 执行中、评审中、子流程中的结构修改首轮不热应用；A 必须显示受影响项，待停止并确认后才能应用新计划。插入排队工作或补充指令走独立命令。
- 应用 AI 嵌套草案必须原子转换；失败不留下半棵树，重试不重复创建子任务。工作树查询不得因显示位置而扩大祖先材料权限。

以上不改变本批边界：当前已实现不可变计划快照与同任务嵌套编辑；子任务转换及权限应在人工节点闭环之后作为独立批次，不能用草稿画布声称这些规则已验收。

## 最小交接样例

以下是边界提案，`inputDescription/outputDescription/assetRefs/expertRef` 为待补到 B NodeHandoff 的字段，**不是声称 B 已支持**。

```json
{
  "nodeId": "node-api",
  "taskId": "task-orders",
  "workflowVersionId": "task-orders-v1",
  "revision": 1,
  "goal": "实现订单查询接口，保持既有调用兼容",
  "assignee": { "id": "chen", "kind": "human" },
  "dependencyNodeIds": ["node-contract"],
  "reviewRequired": true,
  "reviewerIds": ["lin", "qa"],
  "inputDescription": "读取已通过评审的接口约定",
  "outputDescription": "接口实现与测试说明",
  "inputRefs": [],
  "assetRefs": [{ "id": "api-skill", "kind": "skill", "planSnapshotId": "task-orders-v1" }]
}
```

当前 A 通过 `createExecutionHandoff()` 导出 AppliedPlan，含不可变人员/资产内容快照。第一版资产版本用“计划快照 ID + 资产 ID”定位历史定义，不把可编辑的目录 ID 伪装成不可变版本；后续独立资产版本库可无损替代。专家定义同理。输入文字说明与可读取的 ArtifactVersion/ContextPack 引用分开；空 inputRefs 不是产物缺失的自动补造。真实引用由 B/context 按依赖、版本和权限解析。凭据不进入快照。

## 首次联调与集成

链路：A 确认一个人工节点 → B 生成执行对象与待办 → 文字/文件提交 → 两位评审人通过或退回重提 → 下游可处理 → A 显示 B 的状态和产物版本。

联调检查：双窗口版本冲突；同请求重试；修改草稿不改变执行快照；任意一票未通过不推进；旧提交/旧轮次不改变当前状态；子任务返回不跳过父评审。

B PR 目标 main，A 分支 develop。可选择 B 修复并审核合入 main 后将 main 正常合并进 develop，或在独立集成分支合并已验证的两方提交。前者基线更简单；不在带未提交改动的工作区直接拉入 PR。`agent-core/src/index.ts` 保留双方导出，文档状态需要合并。本文不执行合并或重置。
