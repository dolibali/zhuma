# 产品与功能导读

铸码 Zhuma 面向需要共同完成研发任务的团队：负责人组织目标与分工，研发和测试人员处理具体工作，Agent 专家参与分析、实现、验证和评审。工作从需求开始，通过明确的步骤、真实工程操作和版本化交付推进。

## 解决什么问题

团队使用 AI 编码时，还需要回答几个协作问题：需求和资料是否一致、每一步由谁负责、生成结果如何检查、修改意见如何落实，以及下一位成员应该使用哪个版本。

铸码将这些信息关联到任务及其工作节点。负责人可以查看整体进展，成员可以定位自己的待办，评审人可以对照具体提交核查内容，后续工作可以继续使用已经接受的成果。

## 核心设计与价值

| 设计               | 产品中的使用方式                                             | 对团队工作的帮助                           |
| ------------------ | ------------------------------------------------------------ | ------------------------------------------ |
| 目标驱动的 AI 规划 | 输入目标与资料，结合参与者和资源生成步骤，再由团队调整和确认 | 将目标转为可分工、可检查的工作安排         |
| 多层级人机协作     | 节点可拆分子工作流，每步安排成员或 Agent 专家，并配置评审人  | 负责人查看整体结构，成员聚焦具体职责       |
| 本机执行与共享协作 | 成员选择已授权工作区和执行方式，共享服务保存任务、提交与评审 | 团队协作连接各成员已有的开发环境           |
| 固定版本交付       | 提交文字和文件，对指定版本评论、退回、修改和重提             | 把评审意见与被检查的实际内容对应起来       |
| 团队资产复用       | 文件、工作流、Skills 和 Agent 专家集中维护，按项目选用       | 将资料和工作方法用于后续项目，减少重复配置 |

这些价值来自产品的工作组织与数据关联方式；量化效率应使用实际任务耗时、返工和检查记录评估。

## 各角色如何使用

| 角色           | 主要操作                                                   | 关注的信息                                 |
| -------------- | ---------------------------------------------------------- | ------------------------------------------ |
| 项目负责人     | 创建项目和任务，选择参与者，确认计划、分工与评审安排       | 整体进展、依赖、待处理事项及交付版本       |
| 研发人员       | 从待办进入节点，在本机工作区处理工程，提交代码与说明       | 已确认的需求、方案、允许修改范围及评审意见 |
| 测试与评审人员 | 对照需求场景执行检查，查看文件和报告，给出具体意见         | 被检查版本、命令与结果、保持行为及未覆盖项 |
| Agent 专家     | 按节点职责和已绑定 Skills 处理工作，读取有权资料并提交结果 | 明确输入、工具权限、交付要求和停止条件     |

## 一项研发任务如何推进

以下使用预置的[“需求到代码验收”工作流](../resources/workflows/engineering-starter/README.md)说明典型路径。模板可复制和自定义，角色须绑定实际成员或专家，资源与权限须在执行前准备好。

1. **明确需求**：负责人描述目标并关联需求说明、项目资料；需求节点整理本次要做什么、保留什么，以及如何判断结果符合要求。
2. **确认方案与分工**：AI 规划或模板生成步骤，团队在列表、工作流和节点面板中调整职责、依赖、Skills 与评审人；复杂工作可进一步拆分和查看工作树。
3. **在真实工程中执行**：成员从“我的工作”进入节点，选择原生 Agent 或码道 CLI，以及已授权的本机工作区；执行会话保存消息和工具记录。
4. **检查实现结果**：具备相应工具权限的执行者运行工程自己的检查命令，保存代码版本、命令、退出码和报告；实际失败交实现者修正并复验。
5. **评审并修改重提**：实现者提交代码、说明与报告；独立评审者和指定人工评审者核对同一固定版本，退回意见由负责人修正后以新版本提交。
6. **交付与继续复用**：交付节点使用已经接受的版本，后续成员查看有权成果；常用资料、技能和工作流程可留在团队资产中继续选用。

默认工程模板包含“需求澄清、设计与任务、代码实现、验证与失败反馈、送审与修正、固定交付”六个节点。节点执行、运行工作流和子工作流导航各有自己的支持范围；完整工作树自动执行仍按[当前版本边界](release-v1.5.1.md#来源与验证边界)核对。

## 工程案例与结果核验

仓库提供[订单 CSV 导入工程案例](../examples/engineering-demo/README.md)，包含真实 HTTP API、浏览器页面、项目测试和独立验收器。示例保留待实现的编码校验、空行处理和重复订单号检查等需求，供参与者在独立工作区修改并核对前后结果。

| 需要核对的内容       | 可查看的位置                                                                                                 |
| -------------------- | ------------------------------------------------------------------------------------------------------------ |
| 需求与验收条件       | 示例的 [task.md](../examples/engineering-demo/task.md) 与需求节点提交                                        |
| 方案、分工与工作方法 | 已确认计划、节点配置和[工程工作流定义](../resources/workflows/engineering-starter/requirements-to-code.json) |
| 实际代码与兼容行为   | 授权工作区、提交的源码或完整补丁、项目测试输出                                                               |
| 检查的版本与结果     | 项目检查记录、独立验收报告和文件摘要                                                                         |
| 评审、返工与交付     | 固定提交版本、对应意见、新版本提交及最终接受结果                                                             |

检查命令成功、Agent 会话结束、产物提交和评审接受是不同的事实。演练时按实际结果记录各环节，保留失败与修改过程；示例基线和模板定义不预填完整任务已经完成。

## 实现与运行方式

产品由领域核心、工程上下文、Host 执行适配和客户端四个包组成。任务、会话、文件与权限保持明确的数据归属，界面通过公开接口展示状态。本机工作区须由成员明确授权，网页成员入口不直接取得本机工具控制权。详细设计见[架构说明](architecture.md)。
