# 实施顺序

## 已建立的骨架

- 四个 TypeScript 包及明确的依赖方向。
- 计划依赖校验、上下文证据快照、执行者选择、多视图 DTO 的初始契约与测试。
- 成员 B 起草的执行与交付契约，见 [WP00](contracts/wp00-execution-delivery.md)。它尚未接入真实执行，项目与计划编排仍待成员 A 对齐。
- 官方 DSH 子模块与固定运行组合记录。
- 构建、检查、环境诊断和 CI 定义。

## G0：最小真实插件链路

在锁定 DSH 上实现一个 Host 插件和一个 Client 页面，通过既有传输获取真实状态；验证加载、卸载、失败和清理。配套 Bundle 应在干净环境安装，不依赖开发机器路径。此阶段再引入实际宿主依赖，不先伪造接口。

## G1：可运行的最小产品

读取测试工程 → 明确任务 → 有界编码 → 捕获候选 → 独立检查 → 人工查看结果。保留取消、错误和中断记录；初版一个工作区只有一个代码写入者。

## G2：产品增强

上下文来源与过期判断、可修订工作流、专家/Skills/Rules/MCP 配置、对话/运行/编排视图、阶段历史、版本化产物和验证失效。

## G3：桌面发行与可选联动

官方桌面承载同一插件组合；实现中性品牌、独立数据目录、退出/重开、打包和更新配置。码道 CLI 在版本、登录、权限、取消和真实产物验证后成为可选执行者。

## G4：交付与提效

确定代表任务和独立验收，对比传统开发、基础执行与增强工作台，记录成本和失败；区分作品自身开发记录与成品应用效果。未采集的指标保持未测，不估算为成果。
